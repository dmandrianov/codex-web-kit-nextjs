# Web Kit v0.10.0

This release strengthens the technical path for Next.js service sites and e-commerce while making the everyday Codex context substantially lighter.

## What changed

- A living Next.js technical baseline now records the documentation boundary and the decisions that must be rechecked when framework behavior changes.
- A technical architecture gate now sits between project preflight and scaffold. It captures the editing workflow and CMS status, exact framework/runtime boundary, hosting shape, sources of truth, data/render/cache rules, security boundaries, locales/markets and critical scenarios.
- Dynamic sites now receive an application-wide flow check before project handoff or production deployment.
- E-commerce now receives a separate operations/payment safety gate covering server-side order recalculation, signed webhooks, idempotency, concurrency, out-of-order events and recovery/reconciliation.
- Server/client/module ownership, provider adapters and multi-instance/serverless deployment topology are checked earlier and carried through setup, quality and handoff.
- The mandatory entry layer is now compact and classifies requests into `status`, `direct`, `staged` or `cross-cutting`. A status question reads only the current snapshot; a small local fix does not load the whole website workflow.
- `INDEX.md` is now an ambiguity fallback instead of mandatory startup context. The Router contains only the staged and cross-cutting transitions.
- Project state is a short current snapshot. Older chronology stays inside the concrete website in `docs/project-history.md`, after a backup and without losing the original text.
- The former large UI and copy references are split into routed modules. Creator work receives only the relevant criteria before render; full critic, accessibility, responsive, commerce and copy checks remain available at quality time.
- New automated gates enforce byte budgets, local-rule visibility, link integrity, rule preservation and ten representative Codex routes.
- New release manifests use `github-release-gh`; the legacy transport remains limited to the historical `0.9.0` bridge.

## Context verification

- The managed Prompt Kit block is below 10 KiB, the Router below 16 KiB and the state template below 8 KiB.
- A 12 KiB project-local rule fixture remains fully visible inside the standard 32 KiB Codex instruction limit.
- All ten fresh read-only candidate sessions selected the expected route, prompt and critical gates without loading an irrelevant full reference.
- The deterministic mandatory-context comparison reduced ordinary routes by 77.2–92.6%. Whole-session input across the ten live comparisons fell by about 32.3%, including model/tool overhead that Prompt Kit does not control.
- Disposable Bootini and Abgdeyka copies completed the verified `0.8 → 0.9 → 0.10` path. Their project code and local rules stayed unchanged, and their large state histories were archived byte-for-byte before compact snapshots were created.

## CMS decision

If the owner will keep changing the site through Codex/AI and normal deploys are acceptable, the default is `CMS status: not needed`. If editors, content managers, marketers or other non-code users need to maintain content, the kit first defines their roles and publishing workflow, then discusses a CMS.

## Existing projects

Existing stages, approved design/content, page and block specifications, local rules and production code remain valid. Do not rebuild a project or add infrastructure only to satisfy the new documents. If `docs/project-state.md` is oversized, back it up and preserve older chronology losslessly in website-local `docs/project-history.md` before creating the compact snapshot. Capture missing decisions and run the new full-flow checks on the next relevant technical, e-commerce, handoff or deployment task.

This is a non-breaking update from `0.4.22+`. Existing dispatcher paths remain valid, no prompt path is removed or renamed, and no extra confirmation is required beyond the normal conflict and integrity checks.

## Distribution
