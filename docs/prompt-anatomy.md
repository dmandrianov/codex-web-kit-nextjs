# Анатомия промпта

Каждый промпт в этой базе должен быть самостоятельным, но узким. Его можно скопировать в Codex, добавить контекст проекта и получить проверяемый результат.

## Базовая структура

```md
# Название промпта

## Когда использовать
Коротко: на каком этапе и для какой задачи.

## Роль Codex
Кем должен действовать агент.

## Цель
Что должно получиться на выходе.

## Контекст, который нужно дать
Какие файлы, ссылки, вводные, скриншоты или решения приложить.

## Ограничения
Что нельзя делать, какой масштаб задачи, какие технологии и правила соблюдать.

## Процесс
Пошагово, но без чрезмерной детализации.

## Output
Точный формат результата.
Артефакт может быть техническим, но сообщение пользователю должно соответствовать `prompts/_knowledge/codex-user-response-quality.md`.
В конце ответа должен быть понятный блок `Следующий шаг`.

## Done when
Проверяемые критерии готовности.

## Follow-up
Какой следующий промпт запускать после этого и когда свериться с router.
```

## Правила хорошего промпта

- Инструкции идут в начале, контекст отделяется отдельным блоком.
- Масштаб задачи ограничен одним этапом, одним документом, одним блоком или одним видом проверки.
- У результата есть явный формат: Markdown, таблица, список файлов, diff summary, checklist.
- После значимого шага Codex сначала объясняет результат, его пользу и нужное действие, затем показывает следующий prompt как служебную деталь и даёт естественную короткую команду для продолжения.
- Есть критерии готовности, которые можно проверить.
- Если нужна реализация интерфейса, промпт не просит делать всю страницу целиком.
- Если данных не хватает, Codex должен сначала назвать недостающие вводные и предложить минимальные разумные допущения.
- В `Follow-up` должна быть связка с `prompts/ROUTER.md` и `docs/project-state.md`, чтобы следующий шаг выбирался по фактической стадии проекта.

## Типовой контекст

В зависимости от этапа к промпту стоит приложить:

- бриф;
- sitemap;
- page spec;
- block spec;
- дизайн-токены;
- скриншоты;
- ссылки на референсы;
- текущие файлы проекта;
- команды запуска и проверки.

## Типовые ограничения

- Не менять соседние блоки без причины.
- Не добавлять зависимости без явной необходимости.
- Не использовать mock-данные там, где уже есть реальные данные.
- Не делать декоративный дизайн без связи с брендом и задачей страницы.
- Не пропускать адаптив и accessibility для пользовательских интерфейсов.

## Дополнение для maintenance-промптов

Maintenance prompt сохраняет ту же базовую анатомию, но явно фиксирует среду и транзакционную границу.

Для update prompt укажи:

- installed baseline `.prompt-kit/manifest.json` и incoming release manifest;
- установленный numeric repository ID из shipped updater/manifest, browser-authenticated private GitHub Organization source с immutable release/asset attestation или явный verified local fallback;
- точный ownership allowlist;
- preflight до записи, backup, conflict policy и rollback;
- обязательную цепочку `01-update → 02-integrity → 04-alignment`;
- запрет взаимодействия с `.git/`, remote, commit и push пользователя;
- правило: новый installed manifest записывается последним.

Для release prompt укажи:

- что работа идёт только в source-репозитории kit;
- source version, changelog и migrations;
- deterministic payload и exact manifest inventory;
- validation assets/checksums до tag, immutable-releases configuration, draft asset verification и post-publish signed attestation;
- required `TERMS.md`, positive repository ID и canonical full name private Organization repository;
- явное подтверждение перед публикацией;
- запрет смешивать release самого kit с deployment пользовательского сайта.

Корневые source metadata и installed `.prompt-kit/*` — разные роли. Промпт не должен предлагать копировать root `CHANGELOG.md` или `MIGRATIONS.md` kit поверх одноимённых файлов проекта.

## Критерии готовности

Хороший `Done when` отвечает на вопрос: как понять, что задача завершена. Например:

- создан документ с нужными разделами;
- каждый открытый вопрос помечен явно;
- блок реализован только в указанных файлах;
- страница проходит lint/type/build;
- визуальная проверка выполнена в mobile, reference desktop и wide desktop viewport по Desktop Canvas Contract;
- следующий промпт можно запускать без дополнительной расшифровки.

## Формат следующего шага

Каждый prompt должен приводить пользователя к понятному продолжению:

```md
Готово: [результат обычными словами]
Зачем это нужно: [польза или снятый риск]
Что нужно от вас: [ничего / одно точное действие]

Следующий шаг: [человеческое название действия или результата]
Зачем: [1 короткая причина]
Чтобы продолжить, напишите: "[естественная короткая команда пользователя]"

Служебно для Codex: `[path к следующему prompt]`.
```

Если следующий шаг невозможен:

```md
Следующий шаг: ничего — [работа завершена / сначала нужен внешний ввод]
Почему: [короткое объяснение обычными словами]
```
