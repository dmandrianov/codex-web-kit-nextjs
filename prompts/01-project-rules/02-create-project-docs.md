# Создать базовую документацию проекта

## Когда использовать

После финального `project-brief.md` и добавления `Project-specific context` в `AGENTS.md`, до технической настройки, дизайна и верстки.

## Роль Codex

Ты действуешь как product-minded frontend engineer, который готовит понятную документацию для будущих итераций.

## Цель

Создать минимальный набор проектных документов, чтобы router Prompt Kit и дальнейшие промпты могли ссылаться на стабильный контекст проекта.

## Контекст, который нужно дать

- `AGENTS.md`.
- `project-brief.md`.
- `docs/project-state.md`, если он уже есть.
- Краткое описание сайта.
- Текущая структура проекта.
- Известные команды и ограничения.
- Любые бренд-материалы или вводные.
- Правила документации и комментариев из `Project-specific context`.

## Ограничения

- Не проектируй весь сайт в этом промпте.
- Не создавай лишние документы "на будущее".
- Не дублируй содержимое `AGENTS.md`, только расширяй его ссылочными документами.
- Не создавай sitemap, дизайн-систему, page spec или block spec на этом этапе.
- Не заполняй неизвестные факты как подтвержденные.
- Не оставляй документацию в заведомо устаревшем состоянии: если обнаружил расхождение между docs и проектом, зафиксируй его как TODO или исправь в рамках этого промпта.

## Процесс

1. Проверь `project-brief.md`, `AGENTS.md` и текущую структуру проекта.
2. Создай краткий `README.md`, если его нет или он пустой.
3. Создай папку `docs/`, если ее нет.
4. Создай или обнови минимальные документы:
   - `docs/project-state.md` - стадия, артефакты, решения, вопросы, следующий промпт.
   - `docs/project-rules.md` - расширенные правила проекта, если `AGENTS.md` нельзя держать коротким.
   - `docs/decisions.md` - принятые, отложенные и отклоненные решения.
   - `docs/commands.md` - команды запуска, проверки и сборки.
   - `docs/open-questions.md` - вопросы, которые нельзя закрыть из текущих вводных.
   - `docs/materials-index.md` - список исходных материалов, если они есть.
   - `docs/documentation-guidelines.md` - когда и какие документы обновлять, если этих правил нет в `docs/project-rules.md`.
5. Отметь пустые разделы как `TODO`, если данных пока нет.
6. Убедись, что правила актуализации документации отражены либо в `docs/project-rules.md`, либо в `docs/documentation-guidelines.md`.
7. Обнови `docs/project-state.md`: stage `rules-ready`, отмечены `Project docs created`, указан следующий рекомендуемый промпт.

## Output

Список созданных или обновленных документов, краткое назначение каждого и обновленный `docs/project-state.md`.

## Done when

- Есть входная документация проекта.
- Документы можно использовать как контекст в следующих промптах.
- `docs/project-state.md` существует и содержит следующий рекомендуемый промпт.
- `docs/commands.md` фиксирует известные команды или `TODO`.
- `docs/open-questions.md` фиксирует неизвестные данные.
- В документации есть правило, что docs обновляются после значимых изменений проекта.
- Не сделаны преждевременные решения по дизайну или структуре страниц.
