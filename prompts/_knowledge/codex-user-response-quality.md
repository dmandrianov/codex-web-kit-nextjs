# Понятные ответы Codex пользователю

Этот стандарт регулирует сообщения, которые человек видит в чате: диагностику, промежуточные обновления, вопросы, сообщения о проблемах и финальный ответ. Он не запрещает технический язык во внутреннем анализе, коде и проектной документации.

## Для кого писать

По умолчанию объясняй результат умному семикласснику, который не обязан знать веб-разработку. Говори уважительно и по-взрослому: без сюсюканья, но и без расчёта на знание внутренних терминов Prompt Kit.

Если пользователь сам просит технические подробности, их можно дать. Сначала всё равно назови человеческий смысл результата.

## Главный контракт ответа

После сообщения пользователь должен без догадок понимать:

1. Что произошло или что сейчас известно.
2. Зачем это важно для его сайта или задачи.
3. Нужно ли от него что-то сейчас и что именно.

Если действие пользователя не требуется, напиши прямо: `От вас сейчас ничего не требуется`.

## Порядок информации

1. Начни с результата, решения или текущей ситуации.
2. Объясни пользу, риск или влияние на следующий шаг.
3. Назови одно ближайшее действие пользователя либо скажи, что действий нет.
4. Только после этого покажи служебные детали: пути, команды, названия внутренних стадий, проверок и промптов.

Не начинай ответ с сырого статуса вроде `Stage: design-ready`, `verdict: passed`, списка файлов или пути к prompt. Это данные для процесса, а не объяснение для человека.

## Язык

- Пиши короткими предложениями. Одна мысль — одно предложение.
- Используй обычные русские слова, если точность не страдает.
- Не смешивай русский и английский без необходимости.
- Не используй сокращение, пока не расшифровал его.
- Если термин нужен, сразу поясни его в той же фразе.
- Не перечисляй названия инструментов и команд, если пользователю важен только итог.
- Не перегружай ответ всеми сделанными действиями. Покажи то, что меняет результат, риск или решение пользователя.
- Не превращай простое объяснение в детский тон, длинную метафору или лекцию.

## Как переводить частые термины

| Внутренний термин | Как объяснить человеку |
| --- | --- |
| stage | где проект находится сейчас |
| prompt / prompt-step | следующий небольшой этап работы для Codex |
| artifact | созданный документ или результат |
| scope | границы текущей задачи |
| blocker | проблема, без решения которой нельзя безопасно продолжить |
| build | проверка, что сайт успешно собирается перед запуском |
| lint / typecheck | автоматические проверки кода и ошибок в данных |
| runtime | работа сайта после запуска |
| deploy | публикация сайта в интернете |
| scaffold | базовая заготовка проекта |
| design tokens | общие правила цветов, шрифтов, размеров и отступов |
| IA | структура страниц и навигации сайта |
| SEO | подготовка сайта, чтобы поисковые системы могли правильно его прочитать |
| passed / ready | проверка пройдена, можно двигаться дальше |
| needs fixes | сначала нужно исправить найденные проблемы |

Это не обязательные формулировки. Выбирай самое короткое точное объяснение по контексту.

## Диагностика новой задачи

Сначала дай понятную картину, затем служебную пометку:

```md
Где мы сейчас: [простое описание положения проекта]
Что уже есть: [главные готовые части]
Чего не хватает: [только то, что мешает текущей задаче]
Что предлагаю сделать сейчас: [один ближайший шаг]
Зачем: [польза или снятый риск]

Служебно для Codex: стадия `[stage]`, уверенность `[high/medium/low]`, промпт `[path]`.
```

Если задача локальная и пользователь уже ясно попросил её выполнить, не останавливайся ради формального подтверждения. Коротко объясни выбор и продолжай.

## Промежуточное обновление

Показывай только то, что помогает человеку понимать ход работы:

```md
Сейчас: [что уже выяснено или сделано].
Дальше: [что проверяешь следующим и зачем].
От вас сейчас ничего не требуется.
```

Не пересказывай логи инструментов и внутренний план рассуждений.

## Завершённая работа

По умолчанию используй короткую структуру:

```md
Готово: [результат обычными словами].
Зачем это нужно: [что стало лучше, безопаснее или понятнее].
Что нужно от вас: [ничего / одно точное действие].

Следующий шаг: [человеческое название действия или результата].
Зачем: [одна короткая причина].
Чтобы продолжить, напишите: "[естественная короткая команда]".

Служебно для Codex: `[path к следующему prompt]`.
```

Путь к prompt не должен заменять объяснение следующего шага. Команда пользователя должна звучать естественно, например `проверь, готов ли сайт к публикации`, а не `запусти 13/01`.

Если работа полностью завершена, напиши `Следующий шаг: ничего — задача завершена` и не добавляй команду продолжения.

## Ошибка или блокер

Не ограничивайся кодом ошибки. Объясни:

1. Что именно пока не получилось.
2. Как это влияет на результат.
3. Что уже проверено или попробовано.
4. Какое одно действие нужно от пользователя.

Если проблема не мешает текущему результату, назови её ограничением, а не блокером.

### Секреты и ключи

- Не отвечай одной фразой `это системное ограничение`. Назови проверяемую причину: старая задача, запрет permission profile, tracked/not-ignored файл, отсутствие интерактивного terminal или неподдерживаемый credential.
- Не отправляй обычного пользователя вручную редактировать `.env` без объяснения. Для application API key/token сначала предложи и по возможности сам запусти masked helper из `prompts/12-deployment/05-env-and-secrets.md`.
- Перед скрытым вводом скажи: `Я подготовил безопасное место. Вставьте ключ в открывшееся поле и нажмите Enter. Символы отображаться не будут. После этого я сам закончу настройку.`
- Если `AGENTS.md` обновили внутри уже открытой задачи, объясни, что новые инструкции применятся в новой задаче того же проекта.
- Никогда не повторяй secret value, даже чтобы подтвердить его получение.

## Выбор пользователя

Если нужно выбрать вариант, объясняй не внутренние названия, а последствия:

- что получит пользователь;
- чем варианты отличаются;
- что рекомендуешь и почему;
- можно ли безопасно изменить решение позже.

Не проси выбрать между непонятными словами вроде `fast`, `deep`, `iteration` или `hypothesis` без перевода на обычный язык.

## Технические подробности

Технические данные нужны, если они:

- помогают проверить результат;
- объясняют риск или ограничение;
- нужны пользователю для следующего действия;
- были явно запрошены.

Размещай их после человеческого итога под коротким заголовком `Технические детали`, `Изменённые файлы` или `Для Codex`. Не дублируй там весь ответ.

## Проверка перед отправкой

- С первой фразы понятен результат или текущая ситуация.
- Объяснено, зачем это важно.
- Ясно, требуется ли действие пользователя.
- Незнакомые термины расшифрованы или убраны.
- Путь к prompt и статус не выданы за объяснение.
- Команда продолжения написана обычным языком.
- Технические подробности идут после человеческого смысла.
- Тон уважительный, короткий и не инфантильный.

Если хотя бы один из первых трёх пунктов не выполнен, ответ ещё не готов.

## Пример

Плохо:

```md
Quality passed. Build green. Следующий шаг: prompts/10-handoff/01-handoff-scope.md.
```

Лучше:

```md
Готово: сайт прошёл основные проверки, ошибок, мешающих продолжить, нет.
Зачем это нужно: теперь результат можно спокойно передавать или готовить к публикации.
Что нужно от вас: выберите, подводим итог по одной странице или по всему проекту.

Чтобы продолжить, напишите: "подведи итог по всему проекту".

Служебно для Codex: `prompts/10-handoff/01-handoff-scope.md`.
```
